# 시설(장소) 예약 시스템

> **2026-07-05 신규 스코프 진입.** 확인사항 5개를 카톡으로 담당자에게 전달, 회의 답변 대기 중.
> 담당자 안내대로 **§2(겹침 처리)·§3(신청 규칙)만 확정되면 개발 시작 가능** — 나머지는 마커 달고 진행.

## 목적

교인·기관(학교 포함 여부 미정)이 교회 시설(교육실·체육관·홀 등)의 시간대를 온라인으로 신청하고,
관리자가 승인/거부하는 예약 시스템. 달력에서 점유 현황을 확인할 수 있다.

## 결정 잠금 (2026-09-19 · 시설 담당자 회신 + 사용자 확정)

카톡 문의 5건에 담당자가 전부 답했고, UI 구조가 갈리는 4건은 사용자가 확정했다. **아래가 단일 출처다.**

| # | 항목 | 확정 |
|---|---|---|
| 1 | **장소** | 교육실 **1·2·3·4·7·8·10** (5·6·9 제외) · 체육관 · 제1세미나실 · 연합회의실 · 트리니티홀 · 비전홀 · 글로브홀 · **운동장**(학교·동호회). 식당은 추후 |
| 2 | **겹침** | **A안** — 취소되지 않은 예약이 그 시간을 점유한다. 승인 개념이 없으므로 `status='confirmed'` 전부가 대상 |
| 3 | **마감** | **당일 신청 불가** — 시스템 차단 + 안내 문구 둘 다 |
| 3 | **이용 가능 시간** | **08:00 ~ 20:00** (시작·종료 모두 이 안) |
| 3 | **반복** | **5가지 방식** (2026-09-19 담당자 2차 피드백). 각 회차를 **개별 예약 행**으로 만들고 `recurrence_group_id`로 묶는다 — 사이 날짜는 점유하지 않는다 |
| 4 | **승인** | **없음.** 신청 = 확정, 달력에 즉시 표기. `status`는 `confirmed | cancelled` 둘뿐 |
| 4 | **본인 취소** | 신청 시 **비밀번호**를 정하고 그 비밀번호로 취소. **수정 기능은 만들지 않는다 — 취소 후 재신청** (2026-09-18 TF 제안, 사용자 승인) |
| 4 | **학교 신청** | 같은 창구·같은 규칙 |
| 4 | **매크로 방지** | **Cloudflare Turnstile** (사용자 확정). 신청·취소 모두에 적용 |
| 5 | **달력** | 홈페이지 자체 월간 달력. 공개 표시는 **장소·이용기관·용도·시간**까지. **이름·연락처는 관리자만** |
| — | **장소 복수 선택** | 허용. 현행이 자유 입력이라 "1,3,4,8교육실"이 한 건으로 들어오고 있어 실사용 패턴을 따른다 (겹침 판정·달력 표시는 장소별로 분리) |

### 반복 방식 5종 (2026-09-19 2차 피드백 — "일·주·월 단위, 주중(월–금)")

| 방식 | 동작 | 회차 결정 |
|---|---|---|
| 반복 없음 | 기간(시작~종료) **매일** — **일단위 반복이 곧 이것** | 종료일 |
| 주중 (월–금) | 기간 안에서 **토·일 제외** | 종료일 |
| 매주 | 시작일의 요일로 매주 | 횟수 |
| 매월 (같은 날짜) | 매월 같은 **일자** (예: 15일) | 횟수 |
| 매월 (같은 주·요일) | 매월 **N번째 O요일** (예: 셋째 화요일) — **월례회 패턴** | 횟수 |

- **없는 날은 건너뛴다**: 31일(2·4·6·9·11월) · 다섯째 주가 없는 달. 그래서 실제 회차가 요청 횟수보다
  적을 수 있고, 화면이 **만들어질 날짜를 직접 보여 준다** (앞 5개 + 마지막). 추측하게 두지 않는다
- **상한**: 횟수 기반 최대 `MAX_REPEAT_COUNT`(12회) · 기간 기반 최대 `MAX_OCCURRENCES`(60회).
  A안(신청=점유)에서 장기 선점을 막는 장치이기도 하다
- "N일마다"(격일 등)는 넣지 않았다 — 요청에 없고 교회 시설 사용 패턴에 드물다. 필요하면 모드 하나 추가

✅ **상한 확정 (2026-09-19 담당자 피드백): 12회 그대로 간다.** 시설별 차등은 두지 않는다 —
운영해 보고 인기 시설 선점이 실제로 문제가 되면 그때 `MAX_REPEAT_COUNT`를 시설별 값으로 쪼갠다
(`lib/rooms.ts`의 `Room`에 상한 필드를 더하는 정도라 나중에 바꿔도 비용이 작다).

### 폐기된 항목

- ~~`pending` / `approved` / `rejected` 3단계 상태~~ → 승인 단계가 없어져 `confirmed | cancelled`
- ~~3일 전 마감~~ → **당일만** 차단 (현행 안내 문구는 "3일 전"이지만 시스템 차단은 당일 기준)
- ~~관리자만 취소~~ → 비밀번호로 본인 취소

## 2. 겹침 처리 ★가장 중요

같은 장소·같은 시간대에 두 신청이 겹칠 때, **승인 전 신청도 그 시간을 점유한 것으로 볼지**:

- **A안) 신청만 해도 그 시간대는 신청 불가** ← 담당자 추천
- B안) 승인된 것만 불가

> ✅ **A안 확정** (2026-09-19). 승인 단계가 없어져 가용성 판정 집합은 `status = 'confirmed'` 하나다.
> 겹침 방지는 Postgres exclusion constraint(`tstzrange` + `btree_gist`)로 DB 레벨 강제 —
> 동시 제출 레이스 컨디션까지 차단됨. A/B에 따라 constraint의 `WHERE (status IN ...)` 절만 교체.

## 3. 신청 규칙

> ✅ 확정 (2026-09-19): **당일 신청 차단** · **08:00~20:00** · **주간 반복 지원**(개별 행 + `recurrence_group_id`).
> 판정 로직은 `lib/reservations.ts`의 순수 함수로 두고 서버·클라이언트가 같은 함수를 쓴다.

## 4. 승인·관리

> ✅ 확정 (2026-09-19): **승인 없음**(즉시 확정) · 통보 없음(달력이 곧 결과) · **비밀번호로 본인 취소**

- 승인 UI는 어드민(`/admin/reservations`)에 얹음 — `admin-ui.md` 패턴(목록 → 상세 → 승인/거부) 그대로.

## 데이터 (`context/03-data-model.md` §10·§11 — 본 문서와 동시 갱신)

## 사용자 시나리오

1. 방문자가 달력에서 장소·날짜 선택 → 해당일 점유 현황(기관·용도) 확인
2. 빈 시간대 선택 → 신청 폼(이름·연락처·기관·용도·시간) 작성 → 동의 체크 → 제출
3. (A안 기준) 제출 즉시 해당 시간대는 달력에서 "대기" 표시로 점유
4. 관리자가 어드민에서 승인/거부 → 상태 변경 (통보 방법은 미정)
